# 报关申报要素自动校验 SOP

> 版本：v2.0（基于 v1.3 实战版重梳理，融合 SA26090215 委内瑞拉样本复核）
> 定位：可直接用于创建 skill 的完整作业规范
> 适用：出口报关申报要素（品牌 / 型号）与产品实拍标签的自动化交叉校验

---

## 一、任务定义与质量红线

### 1.1 任务一句话定义

> 读取申报要素 Excel，按「出货通知书号 → 成品料号 → 订单号」三级索引定位共享目录下的产品实拍图，对图片执行 OCR，交叉比对 Excel 申报的**品牌**与**型号**，输出带完整证据链的校验汇总表与待人工复核清单。

### 1.2 质量红线（三原则，不可妥协）

| 原则 | 含义 | 违反后果 |
|---|---|---|
| **不虚高** | 宁可判"待人工复核"，不可把 OCR 噪声造成的"假异常"当成真异常上报 | 报告失去可信度，业务方被噪声淹没 |
| **不误放** | 每条结论必须附证据（OCR 原文片段 / 图片路径 / 对照记录） | 漏报真实申报错误，构成合规风险 |
| **可追溯** | 详细日志落盘（JSON），记录每条记录的全部 OCR 文本与判定依据 | 无法复核、无法修正、无法复盘 |

### 1.3 判定结果的四类口径

| 判定 | 触发条件 | 处置 |
|---|---|---|
| ✅ **校验合格** | 申报值与图片证据一致；或双方均为"无" | 直接通过 |
| ❌ **校验异常** | 申报值有、图片有但**不一致**；或申报值缺失但图片明确有 | 进异常明细，优先处理 |
| ⚠️ **缺图内标识，人工复核** | 图片无任何品牌/型号文字；OCR 证据不足（残片、噪声大） | 进待人工复核清单 |
| 🔵 **缺图，人工复核** | 共享目录找不到对应图片 | 进待人工复核清单，需补图后重跑 |

> **关键区分**：`校验异常` = 有证据证明不一致；`缺图内标识` = 没找到证据。两者不可混为一谈。

## 二、输入依赖清单

### 2.1 数据源（默认约定 / 用户未指定时）

| 项 | 默认位置 | 说明 |
|---|---|---|
| **申报要素 Excel** | `{项目空间}\原始输入\` 下最新含"申报要素"的 xlsx | 自动扫描取最新；**用户显式指定则以其为准** |
| **标签图片根目录** | `\\172.20.99.220\制造中心\仓储物流部\成品科\{年份}年报关要素图片\` | 其下按 `{人员}\{出货通知书号}\` 查找 |

### 2.2 数据源优先级规则（铁律）

```
用户显式指定位置  >  项目空间默认约定
```

- 用户说了位置 → **必须**按其指定路径执行，绝不擅自改回默认路径
- 绝不盲目扫描默认目录：若默认目录只有旧票数据，会**错跑成上一票**
- 指定路径需在 Phase 1 提前校验存在性，不存在则显式报错，不要等跑到中途才崩

### 2.3 环境变量接口

| 环境变量 | 接受形式 | 未设置时 |
|---|---|---|
| `CUSTOMS_EXCEL` | Excel 完整文件路径（直接用）**或**所在目录（扫描最新含"申报要素"的 xlsx） | 扫描 `原始输入\` |
| `CUSTOMS_SHARE` | 标签图片根路径（等价替换默认共享根，其下仍按 `{人员}\{票号}\` 查找） | 默认共享路径 |
| `MAX_RECORDS` | 本批处理的记录条数上限（规避 2 分钟硬限制） | 全量 |
| `RESUME_LOG` | 断点续跑日志路径（已完成键不回退） | 无断点 |
| `ACCUM_LOG` | 分批累积结果落盘路径 | 无累积 |

> ⚠️ **禁止经 PowerShell 传递含中文的参数**，统一在 Python 脚本内设 `os.environ`，否则中文路径乱码。

### 2.4 目录空间约束（三条铁律）

```
项目空间/
├── 原始输入/          🔒 只读红线：内容绝不允许修改、重命名、删除
├── 成果产出/          ✅ 最终交付物（校验汇总表 + 待人工复核清单）
├── 过程产出/          🔧 过程文件（详细日志 / 断点 / 临时脚本 / 缓存，可清理）
├── 校验脚本.py        ← 常驻脚本
└── 相关文档
```

1. **原始输入只进不改** —— 任何情况下不得写入、改名、移动
2. **产物分流** —— 最终交付物进 `成果产出\`，过程文件进 `过程产出\`
3. **临时脚本归档** —— 探查 / 批次驱动 / 修正脚本一律落 `过程产出\`，不污染根目录

### 2.5 环境与依赖

- Windows 11+（共享路径用 UNC 路径访问）
- Python 3.11+（推荐 3.13）
- 依赖：`openpyxl`、`rapidocr_onnxruntime`、`Pillow`、`numpy`、`opencv-python`
- 共享路径需有域账号**读权限**

### 2.6 迁移检查清单（同事部署时必改三处）

| # | 位置 | 说明 |
|---|---|---|
| 1 | Excel 扫描目录 | 用户名不同需调整（默认改为脚本同目录的 `原始输入\`，相对路径可零修改） |
| 2 | `SHARE_BASE` | ⚠️ **含年份**，跨年必须修改 |
| 3 | `RESULT_DIR` / `PROCESS_DIR` | 输出落点 |

## 三、判定规则口径

### 3.1 数据映射规则

| 字段 | 来源 | 匹配用途 |
|---|---|---|
| 出货通知书号 | Excel 标题行 / 列 | **一级索引**，定位共享目录文件夹 |
| 成品料号 | Excel 列 | **二级索引**，匹配料号子目录（需模糊匹配，忽略 `-0-49` 之类后缀） |
| 订单号 | Excel 列 | **三级索引**，匹配图片文件名中 `&` 之间的部分 |
| 申报品牌 / 申报型号 | 申报要素列正则提取 | 比对基准 |

### 3.2 图片资源匹配规则

**文件名格式**：`{成品料号}&{订单号}&{序号}.jpg`

```
示例：2670202I1&N030107-002708-001&001.jpg
       └─料号──┘ └───订单号────┘  └序号┘
```

**匹配策略（按优先级）**：
1. **料号目录匹配**：进入 `{票号}\{料号}*\` 子目录（模糊匹配，容忍后缀）
2. **订单号二次筛选**：同料号多订单时，**必须**叠加订单号精确定位，禁止取全部同料号图片
3. **子目录兜底扫描**（subfolder-scan 模式）：当 Excel 无订单号列时，扫描 `{订单号}-0-{箱数}\` 形式的子目录
4. **根目录直放兜底**：图片直接放在票号根目录时按文件名解析

### 3.3 图片类型与信息分布规律（重要）

单条记录通常有 2–12 张图，信息分布有规律：

| 图片序号 | 通常内容 | 品牌/型号信息丰富度 |
|---|---|---|
| `&001` | 标签图 / 出货单 / 外箱唛头 | ⭐⭐⭐ 信息最全 |
| `&002` 起 | 产品实物照、线缆印字、PCB 丝印 | ⭐ 需看实物印刷 |

**结论**：**必须全量 OCR**，不能只取第 1 张。品牌/型号可能出现在：
- 标签的 `品牌/Brand` 字段
- 标签的 `产品名称` / `制造商型号` 字段
- **外箱唛头**的 `Brand:` 行（⚠️ 是整机品牌，非本体品牌）
- 实物/线缆上的印刷字（如 `boori E339609`、`GXD-009`）
- PCB 上的 `MODEL:` 丝印

### 3.4 比对判定规则（5 条核心）

| # | 场景 | 判定 |
|---|---|---|
| 1 | 申报品牌/型号 与 图片识别值 **完全一致** | ✅ 校验合格 |
| 2 | 双方均为"无" / 空 / 无标识 | ✅ 校验合格 |
| 3 | 文字有差异、字段缺失、图片无对应字段 | ❌ 校验异常（标注差异明细） |
| 4 | 图片无任何品牌型号文字 | ⚠️ 缺图内标识，人工复核 |
| 5 | 型号不匹配 | ❌ 异常，**必须列出不同点**（逐字符对比） |

**补充约定**：
- 标签无出口标识 → 视为"无品牌"
- 申报品牌为"无/空" 且 标签也无品牌 → **判合格**
- 型号不一致时必须输出差异点，不能只写"不一致"

### 3.5 防误提取规则（8 条血泪规则）

> 这些是实战踩坑沉淀，直接决定"不虚高"红线是否守得住。

| # | 陷阱 | 规避规则 |
|---|---|---|
| 1 | **字段名被当成值** | 建立字段名黑名单（`制造商全称`/`原产地`/`MFR P/N`/`Supplier Code`/`创维物料编号`…），提取到的值若在黑名单内则判为空 |
| 2 | **值在字段名上方** | 标签表格 OCR 行序可能错位，需在字段名**前后 3 行**窗口内搜索有效值，而非只看下一行 |
| 3 | **"创维"被误当品牌** | "创维物料编号"是字段名，全文搜索品牌时须排除该上下文 |
| 4 | **零宽字符污染** | 要素文本含 `\u200b` 等不可见字符，导致尾部清洗失效（`\s` 不匹配 `\u200b`），解析入口须先剥离不可见字符 |
| 5 | **"适用于某品牌"语境** | 捕获词前若有 `适用于`/`用于`/`适用`，须跳过——那是适配对象不是申报品牌 |
| 6 | **中文品牌漏提取** | 正则须同时支持 ASCII 品牌（`COOCAA`）与中文品牌（`宇同`），且支持单"牌"字格式（`SAMSUNG牌`） |
| 7 | **型号脏尾** | `A7A01G ，电视机用/` 这类需清洗：从头部锚定取首个 ASCII 型号主体，**不可用贪婪 `.*` 截断**（会误伤 `2.402GHz`） |
| 8 | **外箱整机品牌混淆** | 唛头上的 `Brand:Daewoo` 伴随 `Customermodel`/`CARTON`/`JOBNO` 上下文时，是**整机适配品牌**，不构成零部件本体品牌证据 |

### 3.6 多订单区分规则（强制）

> **同料号多订单必须叠加订单号二次筛选，禁止直接匹配全部同料号图片** —— 这是防串货混淆的核心约束。

## 四、标准操作流程（8 Phase）

```
Phase 0  数据源裁定     → 判用户是否指定位置，校验存在性，记录待设变量
Phase 1  Excel 结构探查 → 识别 Sheet 变体、定位表头、提取记录
Phase 2  解析 dry-run   → 验证解析质量 + 图片匹配命中率，跑回归测试
Phase 3  分批 OCR       → 按批次执行（规避 2 分钟硬限制），断点续跑
Phase 4  结果审查       → 统计分类 + 深挖异常证据
Phase 5  人工看图兜底   → 对疑似 OCR 噪声，复制图片逐一视觉核对
Phase 6  修正误判       → 基于看图结论改判，幂等重跑
Phase 7  清理与交付     → 清临时副本，产物分流落盘
Phase 8  同步与留痕     → 同步引擎到 skill、写日志、记录待沉淀项
```

### Phase 0 · 数据源裁定

1. 判断用户是否显式指定 Excel / 图片位置
2. 指定 → 校验路径存在性；不存在 → 显式报错并请用户确认
3. 未指定 → 扫描 `原始输入\` 取最新含"申报要素"的 xlsx
4. ⚠️ **绝不盲目扫描**：先确认目标票号与默认目录内容是否一致

### Phase 1 · Excel 结构探查

**必须先探查，不可假设结构**。已知结构变体：

| 变体 | 特征 | 定位要点 |
|---|---|---|
| **A 老结构** | 首行即表头，含"出货通知书号"列 | 直接按列名取 |
| **B 制单 Sheet** | 有独立 Sheet，标题形如 `出货通知书号:SA...`（**有冒号**） | 标题含冒号 |
| **C 制单 Sheet 无冒号** | 标题形如 `出货通知书号SA...`（**无冒号**） | 兼容两种写法 |
| **D 双 Sheet 结构** | Sheet1 是箱明细（108 列，首列表头恰好叫"出货通知书号"）；**Sheet2** 才是要素表 | ⚠️ 原逻辑会误中 Sheet1；且标题可能缺"书"字写作"出货通知**号**SA..." |
| **E 无订单号列** | 要素表无"订单号"列 | ⚠️ 原逻辑回退取料号列 → order_no 退化 → 图片全失配；须置空 + 启用子目录兜底扫描 |

**表头列名变体**：
- "中文品名" / "名称"
- "出货通知书号" / "出货通知号"
- 申报要素列可能带空格或位于末列

**定位逻辑要区分**：标题行（单单元格含票号）vs 表头列名行，二者判定条件不同。

### Phase 2 · 解析 dry-run

1. 跑解析，输出记录清单（成品料号 / 订单号 / 申报品牌 / 申报型号 / 图片命中数）
2. **逐条人工核对解析质量**，重点看：
   - 品牌是否漏提取（中文品牌、单"牌"字）
   - 型号是否有脏尾
   - 图片命中率是否异常低（0 命中 = 结构适配有问题）
3. 跑**回归测试**：历史用例必须全过，新格式补入回归集
4. 发现解析错误 → **修脚本规则 → 补回归用例 → 重跑**

### Phase 3 · 分批 OCR

- **批次大小**：常规 6 条/批；图片多的票（电源板/主板 7–12 张图）**降到 3–4 条/批**
- **规避 2 分钟硬限制**：单批耗时逼近 120s 即缩批
- **断点续跑**：按 `出货号|料号|订单` 记录已完成键，重跑不回退
- **逐条落盘**：每完成一条即写累积日志，防中途崩丢数据
- 建议后台运行 + 给足超时

### Phase 4–6 · 审查 → 看图 → 修正

**审查**：把异常按成因归类

| 异常类型 | 典型特征 | 处置 |
|---|---|---|
| OCR 噪声虚高 | 字段名误读（`IFR PIN` = `SKYWORTH P/N`）、残片 | 对照同票其他记录 → 改判合格 |
| 等价证据 | 中文名=拼音（`宇同`=`YUTONG`）、制造商名=申报品牌 | 改判合格 |
| 外箱整机品牌 | `Brand:Daewoo` + `CARTON`/`JOBNO` 上下文 | **保留异常**，进人工复核 |
| 证据不足 | 印字仅残片、型号噪声大 | 进人工复核 |

**看图兜底（红线强制）**：凡疑似 OCR 噪声，**必须**复制图片到 `过程产出\` 逐一视觉核对。典型场景：
- 倒置插头：OCR 读成 `600-CX9`，实际是 `GXD-009` → 改判合格
- 短型号 + 易混字符：必须看图确认

**修正**：写修正脚本落 `过程产出\`，采用**基于 key 的幂等赋值**（可重复执行覆盖）。

> ⚠️ 修正脚本常见 bug：值为"带括号但无逗号的字符串"时，`value[0]` 取到首字符（如"零部件"的"零"）。务必确认数据结构是真元组。

### Phase 7–8 · 交付与留痕

- 清理看图临时副本
- 产物分流：汇总表 + 复核清单 → `成果产出\`；日志 → `过程产出\`
- 同步修复后的引擎到 skill 副本
- 写工作日志 + 记录待沉淀项

## 五、技术陷阱与规避

| # | 陷阱 | 规避 |
|---|---|---|
| 1 | **2 分钟单命令硬限制** | 分批执行，单批 3–6 条，后台运行 |
| 2 | **resume / accum 不同步** | 两者按同一 key 写入，逐条落盘 |
| 3 | **中文参数经 PowerShell 传递乱码** | 统一 Python 内 `os.environ` 赋值 |
| 4 | **子进程输出编码报错** | 设 `PYTHONIOENCODING=utf-8` |
| 5 | **官方打包器用 GBK 读文件** | 用 `PYTHONUTF8=1` 强制 UTF-8，不改内置脚本 |
| 6 | **OCR 字符混淆** | `0/O`、`1/I/l`、`9/K`、`8/B`，短型号尤其严重 → 必须看图 |
| 7 | **标签字段留空率极高** | 制造商标签的品牌字段常写"无品牌"或留空，不能据此判异常 |
| 8 | **ERP 描述与 PCB 丝印系统性不一致** | 属厂内码差异（如 ERP `9KC9T` vs PCB `A9KB9G`），**不构成异常证据** |
| 9 | **PowerShell `Move-Item` 到不存在目录 + 尾反斜杠** | 会**静默改名**第一个源文件（而非报错）→ 先建目录再移动，或整体复制 |
| 10 | **ReadOnly 模式无 dimensions 属性** | 调整读取方式或改用普通模式 |
| 11 | **Excel 表头与实际数据可能相反** | 以共享目录结构反推真实映射，不盲信列名 |
| 12 | **Python 环境路径** | venv 的 python 在 `envs\default\Scripts\python.exe`，不在 `envs\default\` |

## 六、汇报规范

交付时按以下结构输出：

1. **数据源说明** —— 用了哪个 Excel、哪个图片目录、多少条记录
2. **统计表**

| 校验结果 | 条数 |
|---|---|
| ✅ 校验合格 | n |
| ❌ 校验异常 | n |
| ⚠️ 缺图内标识，人工复核 | n |

3. **异常明细表** —— 料号 / 品名 / 结果 / 说明（证据）
4. **误判修正说明** —— 改判了哪些、依据是什么（体现"不虚高"红线）
5. **脚本适配说明** —— 本次修了哪些规则、回归测试结果
6. **优先处理建议** —— 哪些最该先看

### 8.1 流程口诀

裁定数据源 → 探结构 → 验解析 → 分批 OCR → 审证据 → 看图兜底 → 修误判 → 交付留痕
   ①            ②        ③         ④          ⑤         ⑥          ⑦         ⑧

### 8.2 三条铁律

1. **数据源铁律**：用户指定优先，绝不擅改用户指定路径
2. **原始输入铁律**：只进不改，绝不写入/改名/删除
3. **不虚高铁律**：疑似 OCR 噪声必须看图确认，不许直接上报

### 8.3 分发清单

- 打包内容：`SKILL.md` + 核心脚本 + 模板脚本 + `SOP.md` + `README.md` + `evolution-log.md`
- 导入方式：解压到 `C:\Users\<用户名>\.workbuddy\skills\`
- 首次部署：核对共享路径读权限 + Python 依赖

### 8.4 自我进化机制

**触发指令**：任务交付后，用户说「复盘」/「总结」/「梳理」（含"回顾一下这次"等义表述）

**进化流程**：
```
回顾识别（新变体/误提取案例/OCR噪声/陷阱/批次经验/口径争议）

```

**四条进化护栏**：
1. 口径变更必须经用户确认
2. 版本号必须递增
3. 改脚本必须跑回归测试
4. 无沉淀时如实说明，不硬凑

### A.1 SA26090084（首次跑通）

- 64 条记录，803 张图，128 个唯一订单号

### A.2 SA26090037 / SA26080766

- 复跑验证流程稳定性，确立模板脚本

### A.3 SA26090334（结构变体 E）

- 10 条记录，26 张图
