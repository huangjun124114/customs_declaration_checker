## 三、安装与使用

### 3.1 单文件 exe（推荐）

1. 把 `报关申报要素校验工具.exe` 放到任意目录（建议专用文件夹）；
2. 双击运行；
3. 首次运行会提示选择 Excel 与图片目录（路径记忆，下次自动回填）。

### 3.2 首次运行后的三步操作

```
1. 选申报要素 Excel（支持本地 / UNC 路径）
2. 选标签图片目录（推荐直接选到「票号目录」那一层：…\{人员}\SA26xxxxxx\）
3. 点「开始校验」→ 结果落在「成果产出」目录
```

### 3.3 自检与环境体检（排错用）

```bash
报关申报要素校验工具.exe --self-test    # 规则加载 + 口径字符串 + 13 列结构
报关申报要素校验工具.exe --check-env    # 环境体检（空壳包检测）
```

## 六、从源码重建 exe（打包机操作）

```powershell
# 1. 全新干净 venv（R11 红线：绝不复用被污染的环境）
python -m venv pack_venv

# 2. 安装依赖（脚本内已含 --no-cache-dir + opencv headless 纠正 + 环境体检）
.\pack_venv\Scripts\python.exe tools\install_deps.py --with-dev --check

# 3. 一键打包（第一步即环境体检，不通过立即中止）
.\build_exe.ps1 -Python .\pack_venv\Scripts\python.exe

# 4. 冒烟
.\dist\报关申报要素校验工具.exe --self-test
```

**打包红线（违反即可能产出带隐藏 bug 的 exe）**：

1. **必须全新干净 venv** —— 否则 pip 中断留下的空壳/残缺包会被烤进 exe，
   而**用户机器无 Python 无法排查**（R11，本项目已累计复发 7 次）；
2. 依赖安装走 `tools/install_deps.py`（自带 `--no-cache-dir` 与 opencv 纠正），
   **禁止**对主依赖使用 `--no-deps`；
3. `tools/check_env.py` **exit 1 必须中止打包**，不得跳过。

> ⚠️ **本机（沙箱）实测补充 —— R11 的真实复发机制**：
> 是**双层拦截**共同造成的，两者都要绕：
>
> | 拦截层 | 现象 | 绕行 |
> |---|---|---|
> | `safe-delete` 钩子拦 `os.unlink` | `pip install` 中途 `PIP_RC=2`、留下空壳包 | **清空 `PYTHONPATH` 后**再执行 pip |
> | 批量删除守卫（阈值 50） | `pip uninstall` / `--force-reinstall` 被 `SIGTERM` 打断 | 抬高 `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD`（如 `1000000`） |
> | 前台命令超时（~120 s） | 长时间 pip 进程被 `SIGTERM`，留下**半安装**包 | **后台执行**（不占前台超时） |
>
> 三者叠加的表现就是「包看起来装上了，其实 dist-info 在、目录没了」——
> 即 §七 新增的**第三类损坏形态**（反向缺体）。

## 七、已知限制

### 7.1 `seq=5` 归属待裁决（规格边界问题）

- **现象**：`seq=5` 申报品牌 `baori`，实测图片品牌取到 `NMY`（离线链路）/ `EMV`（真 OCR 链路），
  判 ❌。但 `baori` 的真实证据确实存在于 `&004` 产品图上。
- **根因**：`rules/non_brand_tokens.yaml` 的非品牌词表**目前只对 ④ 裸 token 层生效**；
  ③「品牌+型号行」层**没有** `non_brand` 过滤 → PCB 丝印残片（同类还有 `NFK`/`SAMYOUNG`/`ONEL`）
  可穿透被当作品牌。
- **性质**：架构裁决 §4.3 的**规格意图**（「元件厂标必须外置到 `non_brand_tokens.yaml`」）
  与 §4.2 的**规格限定**（「该词表仅用于 ④ 裸 token 层」）之间存在边界冲突。
- **处置**：按「**口径变更需确认**」护栏（使用说明 §7 四条护栏之一），
  **本版未擅自改动**。架构师已标注为待裁决项。
- **影响面**：占真实样本 1/18（5.6%），且**偏向保守**（多报异常，不漏放）。

### 7.2 真 OCR 与离线回放存在 9 条品牌取值差异

- `seq 10–18` 两条链路的**品牌取值**不同（OCR 行序与置信度差异所致，如 `Daewoo` 是否被取出）。
- **四类分布完全一致**，四层硬断言均通过，但差异本身未逐条归因。

### 7.3 exe 现场验收待执行（C1 未闭环）

- 本机已产出 exe 并通过 `--self-test` / `--check-env`；
- 但硬约束 C1 的验收标准是「**在干净的 Win10 机器上双击 exe → 界面正常弹出 → 能完成一次跑批**」，
  该现场验收**尚未在执行层如实执行**。

## 八、口径一致性声明

- 本工具**未新增、未改写、未弱化**任何判定口径；
- 四类判定字符串（`core/constants.py`）与 SOP 1.3 **逐字一致**，
  由 `tests/test_constants.py` 硬断言锁定；
- 规则外置（`rules/*.yaml`）改的是**规则的实现载体**，**口径语义完全不变**；
  `tests/test_rule_repository.py` 断言 YAML 与 `constants.py` 默认值一致，防两处漂移；
- OCR 封装库由 `rapidocr_onnxruntime` 升级为 `rapidocr`（**被迫的版本升级**：
  旧库硬卡 `Python < 3.13`），**推理后端仍是 onnxruntime**，属工程实现层变更。

**三条质量红线（不可妥协）**：

1. **不虚高** —— 疑似 OCR 噪声不得直接上报为异常，必须提供看图确认入口；
2. **不误放** —— 每条结论必须附证据（OCR 原文片段 / 图片路径 / 对照记录）；
3. **可追溯** —— 详细日志落盘（JSON），记录每条记录的全部 OCR 文本与判定依据。
