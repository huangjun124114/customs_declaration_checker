## 〇、问题归类与依赖关系

现场 10 点反馈按性质归为 4 类。**类别之间有硬依赖**，实施顺序不能随意。

| 类别 | 原编号 | 主题 | 风险 | 依赖 |
|---|---|---|---|---|
| **A · 交付形态** | 1、2、10 | 目录自动创建 + 控件精简 + zip 文件夹交付 | 低 | 无 |
| **B · 运行期管控** | 3、4 | 运行中锁数据源 + 跑完才进工作台 | 低 | 无 |
| **C · 性能与排程** | 6、7、8、原7-2 | 五阶段排程 + 精准框图 + 并发 OCR + KV 落盘 | **高** | C 内部有序 |
| **D · 复核工作台** | 9（4 子项） | 拖动 / 单图 OCR / 判定链路 / KV 展示 | 中 | **D 依赖 C 的 KV 产物** |

> ⚠️ **关键依赖**：9.3「判定链路说明」与 9.4「KV 按行展示」需要**单图级**键值对数据，
> 而当前引擎只产出**跨图投票后的全局值**。故 **C 类的 KV 提取（点 8）必须先于 D 类完成**。

**建议分三批交付**（每批可独立验收，降低一次性风险）：

| 批次 | 内容 | 特点 |
|---|---|---|
| **批次 1** | A 类 + B 类（点 1/2/3/4/10） | 纯形态与 UI，**不碰判定与 OCR**，风险最低 |

### 1.3 点 10 —— zip 文件夹交付

**现场问题**：单文件 exe 打包问题多，希望改为文件夹 + zip 分发。

**方案**：`customs_checker.spec` 与 `build_exe.ps1` 双改。

| 项 | 现状 | 改为 |
|---|---|---|
| 默认打包模式 | onefile（单文件 149 MB） | **onedir（文件夹）** |
| 产物 | `dist/报关申报要素校验工具.exe` | `dist/报关申报要素校验工具\`（含 exe + 依赖） |
| 分发物 | 单个 exe | `报关申报要素校验工具_v0.2.0_0916.zip` |
| `build_exe.ps1` | 无 zip 步骤 | 新增 `-Zip` 开关：打包后 `Compress-Archive` |

**收益（不只是"降低打包问题"）**：

1. **双击启动秒开** —— onefile 每次启动都要把 149 MB 解包到 `%TEMP%\_MEIxxxxxx`，
   这是你反馈「程序整体运行太慢」的**重要来源之一**（点 6 的一大半可能在这里）；
2. 无 `%TEMP%` 解包行为 → **杀软误报显著减少**；
3. 规则 YAML / 依赖文件**现场可见**，缺文件类问题当场能看出来（v0.1.0 的缺陷 7/9 就是被这个坑到的）；
4. `--check-env` 的打包态降级逻辑不再需要（目录形态下 dist-info 存在）。

> ✅ **Q7 已决**：**接受**「解压后运行」。zip 内直接运行在 Windows 上本就不可靠，代价可接受。

## 三、C 类 · 性能与排程（本轮核心，风险最高）

### 3.1 点 6a —— 五阶段排程重排

**现状链路**（`core/pipeline.py`）：
```
ExcelProbe.probe → ImageResolver.resolve（逐条，四级降级链）→ 逐条 _process_record（条内 max_workers≤2）→ Judge → Export
```

**实测瓶颈定位**（读完代码后的判断，按影响从大到小）：

| # | 瓶颈 | 根因（文件:函数） | 影响 |
|---|---|---|---|
| **B1** | **OCR 全局并发度只有 2** | `core/ocr_engine.py:393` `MAX_WORKERS_LIMIT = 2`（R8 硬夹）+ `core/pipeline.py:686` `_effective_workers()` 每条最多 2；且**记录之间串行** | 113 张图无法并行铺满 CPU，**最大瓶颈** |
| **B2** | **onefile 启动解包 149 MB** | PyInstaller onefile 机制 | 每次启动数十秒 |
| **B3** | **目录被反复扫描（O(N×M)）** | `core/image_resolver.py` 的 `_level1.._level4` 每级都 `scandir`，**每条记录重复扫同一批目录**；18 条记录 × 4 级降级链 | 共享盘上尤其明显 |
| **B4** | **图片全量 OCR，无范围收敛** | `pipeline._process_record` 对该记录所有证据图全跑 OCR | 与点 7 同源 |
| **B5** | 无跨轮缓存 | `core/ocr_engine.py:327` `_LruCache` 是**内存 LRU**，进程退出即失 | 第二轮跑批仍从零 OCR |

**新排程（阶段化 + 单次扫描 + 全局队列）**：

```
阶段 0  预检        校验输入可达性、识别票号、定变体          （现有 PreflightRunner）
阶段 1  Excel 解析  一次性解析出全部记录 + 全部要素键值对      （含点 6b）
阶段 2  框定图片    遍历 {票号} 目录【仅一次】，建倒排索引      （点 7）
阶段 3  并行 OCR    全局任务队列 + N workers，hash 命中直接读缓存（点 5/8）
阶段 4  判定        纯内存计算，毫秒级                        （现有 JudgeEngine，不动）
阶段 5  导出        三产物落盘                                （现有 ResultExporter，不动）
```

**关键改进 1 · 阶段 2 单次扫描（对 B3）**

现状「每条记录 × 4 级降级链」反复 `os.scandir`，改为**一次性建倒排索引**：

```python
{
  "by_order": {"2660310M": [(part_no, seq, path), ...], ...},
  "by_part":  {"N011901-009350-001": [(order_no, seq, path), ...], ...},
  "dirs":     {"2660308M": Path(...), ...}
}
```

每条记录查表 **O(1)**：优先 `by_order[order_no]` 再按 `part_no` 过滤；无订单号（变体 E）时退 `by_part[part_no]` 再按 order 过滤。
**四级降级链保留**作为兜底（索引未命中时才走），但降级时写 WARN 进 notes。
→ **纯算法优化，判定口径零影响**，且共享盘上收益显著。

**关键改进 2 · 全局 OCR 并发池（对 B1）**

现状每条记录内部并发 ≤2 且记录串行 → 全局实际并发 = 2。
改为**全局任务队列 + N 个 worker**，N 由 CPU 核数决定。

> ✅ **Q6 已决**：**放宽到 4–8**。R8 原为防 onnxruntime 线程爆炸，代价是并发度锁死；
> 本轮按 `min(8, cpu_count)` 起步，**先做并发阶梯实测（2/4/6/8）**再定终值（验证计划第 6/7 项）。
> 配套硬约束：**每个 worker 持有独立引擎实例**（见风险 R2），并新增并发一致性断言。

**关键改进 3 · 图像降采样（对 B1，可选 + 高风险）**

实测原图 2448×3264，单张 OCR 2.8–4.7 s。缩放到长边 ≈1600–2000 通常不掉识别率，可再提速 1.5–3×。
但**有识别率风险** → 必须用 SA26090215 全量做 A/B 对照（比对 `text_raw` 差异 + 四类分布是否变化）。

> ✅ **Q5 已决**：**先做 A/B 对照实验再定** —— 实验未出结论前 `resize_long_side = 0`（**默认关闭**）。
> 开启判据：全量 `text_raw` 逐行差异为零，且四类分布与 v0.1.0 完全一致。

**关键改进 4 · onedir 交付（对 B2）** → 见点 10。

### 3.3 点 7 —— 基于订单号 + 物料编号框定图片范围

> ✅ **先纠正一条历史记录（重要）**
> 项目记忆里曾写「文件名格式 = `{成品料号}&{订单号}&{序号}.jpg`」——**这是早期误记，已被 P4 实测推翻**。
> 以实测为准（`core/image_resolver.py:91` 的 `parse_image_file_name` 与 `docs/04` §6.2 一致）：
>
> | 段位 | 含义 | 实测样例 |
> |---|---|---|
> | 第 1 段（A） | **订单号** | `2660310M` |
> | 第 2 段（B） | **物料编号（成品料号）** | `N011901-009350-001` |
> | 第 3 段（C） | **3 位序号**（会跳号） | `001` |
>
> 你这次的描述「文件夹名（对应订单号）+ 图片名称（订单号 & 物料编号 & 3 位序号）」**与实测完全一致** ✅

**方案**：以「**订单号 AND 物料编号**」双条件严格框定，未纳入清单的图片**不参与 OCR**。

**这是点 7 与点 3.1 改进 1 的合体**：索引一次建好，框定变成查表，**同时收敛 OCR 范围**。

### 3.4 点 8 —— 多线程识别 + 落盘 + 键值对

三件事，拆开说：

**(1) 多线程识别** → 见 3.1 关键改进 2（全局并发池）。

**(2) 以图片 hash 为索引落盘** → 见点 5（下方 3.5）。

**(3) 键值对（KV）提取**
新增 `core/kv_extractor.py`，对每张图的 OCR 行做键值对识别：

```
Brand:Skyworth     → {"Brand": "Skyworth"}
品牌：创维          → {"品牌": "创维"}
MODEL:HS-8AA       → {"MODEL": "HS-8AA"}
MFR P/N: xxx       → {"MFR P/N": "xxx"}
```

- 规则**全部外置** `rules/ocr_kv_patterns.yaml`（字段别名表 + 分隔符 + 噪声词表）→ 遵守 C2；
- 输出 `OcrText.kv: dict[str,str]`（新增字段，随缓存落盘）；
- 无 KV 的散行文本原样保留（供工作台标签卡展示）。

> ✅ **Q4 已决（用户选定）**：见 §5「Q4 的精确释义」。
> **数据层复用**（判定阶段读缓存，不再重复 OCR）+ **算法层不改**（仍走跨图投票，KV 不进判定逻辑）。

### 3.5 点 5 —— 全要素提取 + hash 存档（消除重复 OCR）

**现状**：`core/ocr_engine.py:327` 的 `_LruCache` 是**进程内内存 LRU**（默认 512 条），
**进程一退就没了** → 第二轮跑批仍从零 OCR。这正是你说「二次识别判定无需多次 OCR」没实现的原因。

**方案**：新增 `core/ocr_cache.py`，**内容哈希 → 落盘 JSON**。

```
logs\ocr_cache\{hash前2位}\{hash}.json
```

```jsonc
{
  "schema": 1,
  "hash_algo": "sha256",
  "image_hash": "9f2c…",              // 纯图片内容 sha256（不含任何路径信息）
  "image_size": 1876342,
  "image_path_hint": "…&001.jpg",     // 仅首次识别路径，供排错，不参与命中判定
  "engine":   { "name": "rapidocr", "version": "3.9.2" },
  "params_fingerprint": {             // ⚠️ 关键：参数字段参与命中判定
    "resize_long_side": 0,             // 0 = 未降采样
    "intra_op_num_threads": 2
  },
  "created_at": "2026-09-16T20:11:03+08:00",
  "lines": [ { "text": "Brand:Skyworth", "score": 0.987, "box": [[x,y],…] } ],
  "kv":     { "Brand": "Skyworth" },
  "text_raw": "Brand:Skyworth\nMODEL:HS-8AA\n…",
  "low_confidence": false
}
```

| 设计点 | 决策 | 理由 |
|---|---|---|
| 缓存 key | 图片内容 sha256（**非路径**） | 同一张图在不同路径/UNC 映射下只 OCR 一次（`_compute_image_hash` 已实现此逻辑） |
| 失效条件 | `engine.version` 或 `params_fingerprint` 不一致 → **视为未命中** | 引擎升级或降采样参数变更后，旧结果不可信 |
| 命中收益 | 直接读 JSON，**秒级** | 第二轮跑批 OCR 阶段接近 0 耗时 |
| 落点 | `logs/ocr_cache/`（过程产出） | 遵守「产物分流」铁律 |
| 清理 | 菜单新增「清空 OCR 缓存」 | 避免无界增长（预估 113 张 × ~20 KB ≈ 2 MB/票） |

> ⚠️ **与点 6a 的耦合**：若启用降采样（Q5），`params_fingerprint` **必须**包含该参数，
> 否则新旧结果混用 → 判定不可复现。这是硬约束。

### 4.1 点 9.1 —— 支持拖动（放大后可平移查看）

**现状缺陷定位**（`ui/widgets/image_viewer.py`）：

**修法**：
1. `setWidgetResizable(False)`；图片小于视口时用 `scroll.setAlignment(AlignCenter)` 居中，大于视口时按需出现滚动条；
2. 新增**鼠标左键拖拽平移**：`mousePressEvent` / `mouseMoveEvent` / `mouseReleaseEvent`

3. `Ctrl + 滚轮` 缩放保留（现状已有，不动）。

**这是一个明确的 bug 修复，不涉及设计取舍。**

### 4.2 点 9.2 —— 切换图片时只显示当前图的 OCR

**现状缺陷定位**（`ui/widgets/workbench_card.py` `_render_evidence()` 第 183 行）：

### 4.3 点 9.3 —— 证据/重判区说明「四段式判定链路」
