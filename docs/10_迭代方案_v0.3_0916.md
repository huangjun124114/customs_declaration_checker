## 1. 现状复盘（为什么必须改）

### 1.1 现链路的结构性缺陷

```
OCR 原文 ──► extract_detected_brand()   ← 四层正则 + 跨图投票「猜」出图片品牌
             extract_detected_model()   ← 正则「猜」出图片型号
                    │
                    ▼
          NoiseGuard.classify_detail(申报值, 识别的值)  ← 只有「猜到值」之后才能比对
```

**问题**：比对的前提是「先正确猜出图片侧的字段值」。而 OCR **缺失空间感知**（无左右/上下关系），
导致：

- 字段名与值不在同一可见行（唛头版式里 `Brand:` 与值常分列）→ 正则窗口抓不到 → 取值为空；
- 值被误抓成相邻字段名残片（`SKYWORTH P/N` → `SKYWORTH`）；
- 多层正则 + 投票带来「不可解释」——用户看到 ❌ 却不知道为什么。

**用户反馈「key-value 出现缺失，进而出现误判」正是这条链路的必然结果。**

## 3. 需求 1 详细设计（核心）

### 3.1 已确认的四项口径（用户 2026-09-16 拍板）

| 决策项 | 结论 |
|---|---|
| 未命中如何判 | **两级分流**：图内有同类标识但值不同 → ❌；图内无该类标识 → ⚠️ |
| OCR 误读容错 | **保留**：沿用 `known_noise_samples` + 易混字符表，纠正后仍算命中，判定值栏标注「OCR 疑似误读，已纠正」 |
| 分词切分口径 | **英文/数字按词边界**（`JYB` 命中 `品牌:JYB`、`JYB-100`；**不命中** `JYBA01`）；**中文按子串**（`宇同` 可命中 `宇同电子有限公司`） |
| 状态标签分类 | 全部 / 成功 / 待复核(⚠️) / 缺图(🔵) / 失败，**缺图单列** |

### 3.2 新增模块 `core/token_matcher.py`

```python
@dataclass
class TokenMatch:
    field: str            # "品牌" / "型号"
    declared: str         # 申报值原形
    mode: str             # "EXACT" | "FUZZY" | "NONE"
    token: str            # 命中的 token 原形（EXACT/FUZZY 时非空）
    images: list[int]     # 命中所在图片序号（可多个，供 UI「命中来源图号」）
    sample_line: str      # 命中所在 OCR 原文行（截断 120 字，供 UI 展示与追溯）
    corrected_from: str   # FUZZY 时：OCR 原始误读形态
    note: str             # 人类可读说明

class TokenMatcher:
    def __init__(self, texts: list[OcrText], rules: RuleRepository | None = None) -> None: ...
    def match(self, declared: str, *, field: str) -> TokenMatch: ...
```

**匹配算法（三级）**

1. **EXACT（精确完整分词）**
   - 英文/数字：正则边界匹配 `(?<![A-Za-z0-9]){VALUE}(?![A-Za-z0-9])`（`re.IGNORECASE`，对每张图的 `text_raw` 全文检索）
   - 中文：子串包含（`VALUE in line`）
   - 值长度 < 2 → 不参与（沿用 `_MIN_BRAND_LEN`）
2. **FUZZY（OCR 误读纠正）**
   - 命中 `noise_signals.yaml::known_noise_samples` 的 `expected_actual` 映射 → 纠正后重跑 EXACT
   - 或命中易混字符等价类（`O↔0`、`I↔1↔L`、`W↔H↔N`、`S↔5`、`B↔8`、`G↔6` 等）→ 归一化后重跑
   - 命中 → `mode=FUZZY`，`corrected_from` 记 OCR 误读形态
3. **NONE** → 走 §3.3 两级分流

**⚠️ 必做护栏：字段名上下文剔除（防新链路引入虚高）**

中文按子串匹配会带来新风险：申报品牌 `创维`，而图上有 **`创维物料编号`** 这个**字段名** → 子串命中 → 误判 ✅。

对策（已实现，`core/token_matcher.TokenMatcher._is_field_name_context`）：命中后检查**右侧紧邻**文本，
三道判据任一成立 → **该命中作废**：

| 判据 | 触发形态 | 举例 |
|---|---|---|
| **G1-CJK** | 命中右侧**紧邻**位置即为中文字段名后缀 | `创维` + `物料编号` → `创维物料编号` |
| **G1-ASCII** | 命中右侧（跳过空白）以英文字段名后缀**词边界**开头 | `SKYWORTH` + ` P/N`、`Manufacturer` + ` Name` |
| **G2** | 从命中位置向右延展的连续文本归一化后等于 `fields_blacklist` 词条 | `MFR P/N` 整串 |

- 后缀词表：CJK `物料编号/编号/代码/名称/全称/地址/日期/数量/原产地/供应商/制造商/生产厂商/批次`；
  ASCII `P/N、P/H、PIN、NO、NO.、NUMBER、CODE、NAME、ADDRESS、DATE、QTY、MFR、SUPPLIER、MANUFACTURER、BATCH、LOT`
  （ASCII 一律**词边界**匹配，防 `N011901` 里的 `NO` 误伤）。
- **同源规则**：已知误读样本的 `expected_actual` 若**本身是字段名**（`SKYWORTH P/N` = 创维物料编号），
  该样本**不作命中依据** —— 否则申报品牌 `SKYWORTH` 仅凭图上字段名就被判合格（同一条虚高路径）。
- 命中被作废时 `TokenMatch.note` 明确写出原因（**不静默丢弃**，可追溯红线）。

（本护栏必须带单测；缺此护栏 = 直接违反「不虚高」红线。实测真实样本上**作废 0 次**，无误伤。）

### 3.3 判定接线（`core/judge_engine.py`）—— 实现后的实际流程

保留全部既有骨架，仅替换「字段状态」的产生方式（`_field_state_v03`）：

```
① 图片证据闸门（不改）
   record.evidences 无有效图 → 🔵 NO_IMAGE（unreachable / not_found 语义不动）

② 字段状态（改）
   if 申报值 为空/「无」:
       → 沿用原链路 _field_state（双方均为无 → 合格；申报无但图片明确有 → ❌）
   else:
       m = TokenMatcher.match(申报值, field)
       if m.mode in (EXACT, FUZZY):
           state = MATCH                    # ✅（FUZZY 附「疑似误读，已纠正」说明）
       elif 噪声三态 == SUSPICIOUS:         # ⚠️ 不虚高红线优先于"未命中即异常"
           state = SUSPICIOUS
       elif 图内识别值非空:                 # extract_detected_* 非空 = 图内有同类标识
           state = MISMATCH                 # ❌ 校验异常（列图内实际标识值）
       else:
           state = DETECTED_MISSING         # ⚠️ 缺图内标识

③ 整机品牌（不改）
   _is_whole_machine_any_image 命中 → 保留 ❌（T06 裁决 A′）

④ 记录级跨文字体系兜底（改：对**已命中字段**豁免）
   is_cross_script → SUSPICIOUS，但 brand_match.hit / model_match.hit 的字段不受影响
   （命中是"直接证据"，优先于"跨文字体系"这类近似推断）

⑤ 降级护栏（不改，红线唯一闸门）
   noise_level == SUSPICIOUS 且 verdict == FAIL → 强制 NO_MARK（⚠️）

⑥ 可追溯（新增）
   判定说明附 TokenMatch.note（命中 token + 来源图号 / 未命中原因 / 字段名护栏作废说明）
```

> **两级分流如何实现「图内有同类标识」**：直接复用现有 `extract_detected_brand()` /
> `extract_detected_model()` **是否非空**作为布尔判据。这样既复用了已过滤字段名残片、非品牌 token
> 的成熟逻辑（缺陷 C 的成果不浪费），又让「有证据不一致」与「没找到证据」仍然分野清晰。

### 3.6 判定范围收窄为「只识别品牌与型号」（v0.3.1 · 用户口径 2026-09-16）

**口径原文**：「申报要素只需要识别品牌和型号，其他要素无需识别、判断」

落地为 `core/constants.py` 两条常量（均进 `__all__`）：

| 常量 | 值 | 作用 |
|---|---|---|
| `JUDGED_FIELDS` | `("品牌", "型号")` | 明确「参与识别与判定的**仅此两者**」，供后续扩展点统一引用（不再散落字面量） |
| `NON_VALUE_FIELD_SUFFIXES` | `("类型", "种类", "类别")` | **非「值」类字段后缀** —— `品牌类型` / `型号类型` 的取值是「品牌的归类」而非品牌本身 |

`core/element_parser.py` 三处候选收窄：

| 位置 | 改动 |
|---|---|
| `_is_brand_key()` / `_is_model_key()` | 命中 `NON_VALUE_FIELD_SUFFIXES` 后缀 → 直接返回 `False` |
| `_extract_brand()` 「含品牌字样段落」分支 | `if self._is_non_value_key(key): continue` |
| `_extract_model()` ②③ 分支 | 同上排除 |

⚠️ **为什么必须补 `NON_VALUE_FIELD_SUFFIXES` 这条护栏**：缺它时 `品牌类型:0` 会被
读成品牌值 `0` → **违反「不虚高」红线**（把一个归类编码当作实物品牌证据）。

> 📌 **性质说明**：这是**防御性加固，不是行为变更**。实测申报要素原文
> `用途:电视机用|结构类型:有接头|品牌:baori|型号:无|额定电压:60V` ——
> `_is_brand_key()` 只认「含品牌字样且不含型号字样」的键，本来就只判品牌 / 型号。
> 本轮重点是堵住既有实现里**「品牌类型 → 品牌值」的潜在虚高入口**。
> 覆盖用例：`tests/test_element_parser.py` 新增 11 条（含 `品牌类型` 4 组参数化）、
> `tests/test_constants.py` 新增 `TestJudgedFieldsScope` 4 条。

### 6.3 「错位覆盖」修复（v0.3.1 · 现场截图 1）

现场现象：「判定原因」文本**压在表格「型号」行上**，表格只见「品牌」一行。

**根因不在表格，在父容器的尺寸分配**（完整实测链见 `CHANGELOG.md` §[0.3.1]）：

```
卡片内容 需 886px  →  实操只拿到 759px（= 滚动视口高）
   ↓ QVBoxLayout 只能在「最小 ~ 首选」间压缩子控件
判定链路框 被压成 190px（其 minimumSizeHint = 194px）
   ↓ 表格有 setFixedHeight(113) 压不动，先挤 wordWrap 标签
「判定原因」拿到 34px 却从 y=109 起画 → 溢出到表格 (30..143) 之上
```

而内容撑不高的**第二层根因**很隐蔽：`QLayout.addWidget()` 用
**queued** `_q_showIfNotHidden` 显示新子控件，`load_result` 里刚 new 的散行标签
在下一拍前仍 `isHidden()` → `FlowLayout` 的 `sizeHint` / `heightForWidth` **一律返回 0**
→「内容需要多高」被测成 0 / 577 / 718（稳定值 886）。

四件套修法：

| # | 修法 | 关键点 |
|---|---|---|
| 1 | 整卡内容套 `QScrollArea`（`widgetResizable(True)`，横向不滚动） | 让"内容超高"变成"滚动"，而不是"压扁" |
| 2 | `_fit_content_height()` 用 **`heightForWidth(视口宽)`** 写回 `content.minimumHeight` | 不能用 `sizeHint`（按"不换行"估算成 1274，会白滚一大截） |
| 3 | `_reveal()`：新增流式子控件显式 `show()` | **最关键**一条；不做则几何查询永远拿到 0 |
| 4 | 表头左对齐 / 关双滚动条 / 前两列 `Fixed` + 第三列 `Stretch` / `_fit_chain_height()` 按表头实际高校正 | 修掉表格自身的次级错位 |

外加 `eventFilter` 监听滚动视口 `Resize`（滚动条出现会挤窄列宽 → 换行数变 → 需重算），
与 `_fitting_content` 重入闸防「内容 resize ↔ 视口 resize」互激。

**底部操作区常驻**（`QFrame#cardFooter`）：内容恢复真实高度后，「重判为 / 备注 /
标记待补图 / 保存重判」会被推到折叠线以下 —— 等于把"压扁"换成"藏起来"，
故 `shell = 滚动区(stretch 1) + 操作区(stretch 0)`。

回归锁（`tests/test_ui_workbench_d_class.py`，均为**被压扁场景**下断言）：

| 用例 | 反向锁断言 |
|---|---|
| `test_chain_frame_is_never_squeezed_below_its_minimum` | `frame.height() >= frame.minimumSizeHint().height()`（回退态 190 < 194 ✗） |
| `test_chain_reason_does_not_overlap_table` | `reason.top() >= table.bottom()`（回退态 109 < 143 ✗） |
| `test_card_content_takes_height_for_width` | 内容最小高 == `heightForWidth`，且**重算 3 次不漂移** |
| `test_flow_labels_are_shown_synchronously_after_render` | **刻意不 processEvents**，断言新标签非隐藏且 `heightForWidth > 0` |

### 8.2 定位重写：右侧垂直居中，不置顶（v0.3.1 · 现场截图 2）

现场现象：弹窗出现在窗口**左上角**，压住图片区与右侧证据卡。

修法：把定位逻辑抽成**纯函数**（可任意分辨率单测，不再依赖真实窗口几何）：

```python
OcrTextDialog.place(area: QRect, win_geo: QRect | None, anchor: QRect | None) -> QRect
```

分级策略（`_GAP = 8` / `_MIN_WIDTH = 360` / `_MIN_HEIGHT = 240`）：

| 级 | 条件 | 位置 |
|---|---|---|
| ① | 图片区右侧可放（`right_edge - left_bound >= _MIN_WIDTH`） | **右对齐窗口右边界 + 垂直居中**（宽度按需收窄，高度夹到 `_DEFAULT_HEIGHT` 与屏高之间） |
| ② | 右侧放不下 | **贴图片区下方**（保住「不遮图」这条硬约束） |
| ③ | 上下左右皆无空间 | 默认尺寸贴右侧 + 垂直居中 |

`show_beside()` 瘦身为 `setGeometry(self.place(...)) + show/raise/activateWindow`；
`_clamp()` 签名简化为 `_clamp(area, rect)`；**删除失效的 `_fits()`**。

回归锁：`tests/test_ocr_dialog_position.py` **15 条**（5 种分辨率参数化右对齐+居中、
**对旧缺陷的反向锁** `rect.top() > 8`、浮动窗不出右边界、无图片区 / 无窗口兜底、
窄区域收窄、屏高不足时仍不溢出、降到图片区下方且不置顶、常量自洽）。
